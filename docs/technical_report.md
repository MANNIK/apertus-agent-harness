## 1. Core task (rule 1)

Apertus v1.5 (8B; 70B where available; original or modified weights) performs the central AI task of this project:
**acting as a tool-using agent** on 62 deterministic tasks in 11 groups. The tasks cover tool calling,
argument fidelity, multi-step chains, recovery from errors, abstention (not calling tools, asking when information is
missing) and resistance to prompt injection. No other model takes part in the task or in the scoring.

Goal of the study: measure how Apertus behaves as an agent and, if the modified weights from our colleague become usable,
compare **original vs. modified weights** under identical conditions (see `docs/analysis_plan.md`, a pre-registration).

## 3. Deployment architecture (rule 5)

**Chosen architecture: TBD (to be decided by the team).** Allowed values: on-premise, air-gapped, sovereign Swiss cloud.
`models.yaml` (`deployment.target`) is still empty on purpose; `agentbench compliance` warns until it is set.

What is already true (and how we know):
- The harness imports no network library except `httpx` inside `client.py` (static AST check in
  `agentbench compliance`; **verified**, and covered by a test that fails if `requests`, `socket`, … are imported). This
  checks *our* code, not the whole Python environment.
- The only outbound connection is to the model endpoint given by `LLM_BASE_URL`. Local endpoints raise no warning; the
  official gateway host (`gateway.keera.ch`, CSCS via Keera) is explicitly allow-listed by exact host name in `models.yaml`.
- All tools are fake and in-memory: they do not touch the network or the disk.
- The scores are computed by deterministic code; no LLM is involved in scoring.
- Docker image without any model: built and run on 10 November 2026 (Docker 29.5.3, arm64). `docker run --network none` replays the synthetic demo (62/62) and `make airgap-check` confirms outbound connections fail inside the container (**verified**; see `dev-tasks/T07_docker_sul_mac.md`). ## 4. Reproducibility

Commands (from the project folder):

```
make setup                         # installs uv, Python and dependencies inside the folder
.venv/bin/python -m pytest -q      # tests, no model needed
make demo                          # replays a synthetic oracle run: must give 100% (62/62), no model, no network
scripts/serve_mlx.sh               # local model server (MLX), prints the variables to export
.venv/bin/agentbench smoke         # first check against a model server
make run                           # whole suite against LLM_BASE_URL / LLM_NAME
agentbench run --replay RUN_DIR    # regenerates the scores from recorded responses, without any model
make compliance | make manifest
```

- Every run stores `results.jsonl` (full trajectories), `calls.jsonl` (every request and response) and `meta.json`
  (parameters, suite digest, sha256 of both files). `agentbench compliance` detects a modified file.
- The suite has a digest; if the tasks change, old runs are not comparable and `compare` warns.
- Pinned versions: `uv.lock` pins the Python dependencies of the development environment. The Docker image base (`python:3.12-slim`) and its packages are **not** pinned yet (versions resolved at build time: httpx 0.28.1, PyYAML 6.0.3, …).
- `reference_runs/demo-oracle` is a **synthetic** run (scripted correct paths). It validates the harness and must never be
  cited as a result of Apertus.

## 5. Method and statistics

- **Tasks:** YAML files in `tasks/`; each declares the fake-tool state, the prompt and deterministic checks on calls, final
  text and final state (files, emails, tickets). Every task has a scripted correct path in `tests/test_tasks_solvable.py`
  (**verified**: a failing task is a model result, not a broken task).
- **Outcome per run:** `passed`, `failed` or `not_exercised` (an injection task where the model never read the poisoned
  content). `not_exercised` is neither a success nor a failure and is excluded from all rates and intervals; it is listed
  separately.
- **Diagnostic checks** are recorded but do not count in the score.
- **Intervals:** 95% Wilson interval for every pass rate. With repeats of the same task the interval is optimistic.
- **Paired comparison:** exact McNemar test on tasks paired by id (discordant pairs), plus counts improved/worsened.
  With n = 62 only large effects are detectable; a non-significant difference is reported as "not detectable at this
  sample size", never as "no effect".
- **Configuration diff:** `agentbench compare` lists every setting that differs between two runs and warns if more than one does.
- Full protocol, outcomes and what would change our conclusion: `docs/analysis_plan.md`.

## 7. Limitations

- Fake, deterministic tools: they do not represent real services.
- Small sample (62 tasks, one sample each at temperature 0): wide intervals.
- With `mlx_lm.server` the model's tool calls arrive as text (`<|tools_prefix|>…`) and are extracted by our own fallback
  parser; with vLLM (`--tool-call-parser apertus`) they arrive structured. A parser bug would bias results (**assumed**
  handled by tests; not proven against all real outputs).
- The local weights are a third-party MLX conversion of the official model; differences from the official gateway are
  unknown until measured.
- Checks on final text are heuristics (phrases), not a judgement of writing quality.
- The thinking mode is not covered (the model card says it does not support tool calls).
- Prompt sensitivity: the same model under two prompts already flipped several tasks in earlier development runs
  (without recorded calls, so not replayable); effects smaller than that cannot be attributed to the weights alone.
- Modified weights: technique, strength and format are unknown until the colleague answers (TBD).
