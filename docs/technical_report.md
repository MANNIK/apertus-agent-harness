# Apertus Weight-Space Lab: targeted weight edits vs. LoRA vs. the original model on Swiss open-data Text-to-SQL

**DRAFT.** Structure complete; every result is a placeholder (`TBD (run: …)`) until a real run exists in `runs/`.

Team: Nikola, Kri, Nathan · Event: Apertus hackathon, Zurich, 27 November 2026.

## 1. Core task (rule 1)

Apertus v1.5 8B performs the central AI task: given a question in German, French, Italian or English about a Swiss
open dataset, it writes a SQL query that is executed on a local, read-only DuckDB database, then states the answer.
The score is **deterministic and by execution**: the result of the model's last successful query is compared with the
result of a gold query (rules in `src/agentbench/sql_eval.py`). No LLM takes part in the scoring.

We compare three conditions under identical inference settings: **(A)** the original Apertus 8B, **(B)** Apertus 8B with
targeted weight modifications (WSP: θ' = θ + Δθ, designed with a development model), **(C)** Apertus 8B with a LoRA adapter
trained under a comparable protocol. We also measure generalisation to unseen schemas, regression on capabilities we did not
optimise, latency, memory, the number and percentage of modified parameters, and the adaptation cost.

The value of the study does not depend on WSP beating LoRA: a modest, interpretable and cheap improvement, or a null result
measured honestly, is a result. A demonstration application (self-hosted data analyst over Swiss open data) is planned: **not built yet** (TBD).

## 3. Deployment architecture (rule 5)

**Chosen architecture: TBD (to be decided by the team).** Allowed values: on-premise, air-gapped, sovereign Swiss cloud.
`models.yaml` (`deployment.target`) is still empty on purpose; `agentbench compliance` warns until it is set.

What is already true (and how we know):
- The harness imports no network library except `httpx` inside `client.py` (static AST check in
  `agentbench compliance`; **verified**). This checks *our* code, not the whole Python environment.
- The SQL tool runs DuckDB **read-only** with file and network access disabled for the model's queries (**verified** by tests:
  INSERT/DROP/COPY/ATTACH/reading files or URLs/INSTALL/multiple statements are refused). The database is built from local CSV files.
- The only outbound connection of the harness is to the model endpoint given by `LLM_BASE_URL`. Local endpoints raise no warning; the
  official gateway host (`gateway.keera.ch`, CSCS via Keera) is explicitly allow-listed by exact host name in `models.yaml`.
- The scores are computed by deterministic code; no LLM is involved in scoring.
- A Docker image without any model existed for the previous project and ran with `--network none` (`dev-tasks/T07_docker_sul_mac.md`);
  it has **not** been re-verified for the new project (the image does not yet contain DuckDB or the data).
- Modified checkpoints cannot be served by the official gateway (it serves the official weights); we serve them ourselves (local MLX or our own server). TBD.

## 4. Reproducibility

Commands (from the project folder):

```
make setup                         # installs uv, Python and dependencies (incl. DuckDB) inside the folder
.venv/bin/python -m pytest -q      # tests, no model needed
make demo                          # replays a synthetic oracle run: must give 100% (8/8), no model, no network
make zurich-tasks                  # regenerates the dataset from data/zurich/ and the specs (deterministic)
scripts/serve_mlx.sh               # local model server (MLX), prints the variables to export
.venv/bin/agentbench smoke         # first check against a model server
.venv/bin/agentbench run --thinking off --tasks tasks/zurich/dev
agentbench run --replay RUN_DIR    # regenerates the scores from recorded responses, without any model
make compliance | make manifest
```

- Every run stores `results.jsonl` (full trajectories), `calls.jsonl` (every request and response) and `meta.json`
  (parameters, task-set digest, sha256 of both files). `agentbench compliance` detects a modified file.
- **Data:** a snapshot of 15 CC0 datasets of the City of Zurich in `data/zurich/` with sha256 in `MANIFEST.json`; the license of each
  dataset is re-read from the portal API when downloading. Task files are generated deterministically and checked by a test.
- **Splits:** by schema and by domain (dev 96 / val 30 / test 84 tasks); the CLI refuses test tasks without `--final-test`.
- Pinned versions: `uv.lock` pins the Python dependencies of the development environment (DuckDB 2.0.0).
- `reference_runs/demo-oracle-sql` is a **synthetic** run (gold queries executed by a script). It validates the harness and must never be
  cited as a result of Apertus.

## 5. Method and statistics

- **Data:** 15 real CC0 tables (population, housing and rents, income, motorisation, social assistance, waste, votes, air quality,
  meteorology, emergency response times, consumer prices) with their original German column names and real quirks
  (numbers stored as text, `NA` and `.` as missing markers, trailing spaces, several index bases). Questions in DE/FR/IT/EN
  are instantiated from ~70 templates by sampling real values; each gold query is **executed** and instances with empty,
  null, zero or tied answers are dropped.
- **Score:** execution accuracy (result-set comparison: multiset of rows, columns by position, NULL = NULL, numeric tolerance;
  see `sql_eval.py`), plus the final answer's number where the result is a single number.
- **Protocol:** dev/val for iterating, test once per condition with frozen configuration; every attempted modification is logged,
  including discarded ones. Full pre-registration (hypotheses H1–H3, Holm correction, schema-cluster bootstrap, feasibility gate,
  matched-budget rule, open decisions): `docs/analysis_plan.md`.
- **Intervals:** 95% Wilson interval for every accuracy. **Paired comparison:** exact McNemar on tasks paired by id, Holm-adjusted over
  the three comparisons. A non-significant difference is reported as "not detectable at this sample size", never as "no effect".
- **WSP method:** TBD (undecided; candidates in `docs/wsp_candidate_methods.md`). **LoRA protocol:** TBD.

## 7. Limitations

- **The questions are not reviewed by native speakers**: German, French and Italian phrasings were drafted by a development model.
- The questions come from ~70 templates: lower diversity than a hand-written benchmark; same-template questions share structure.
- The test set is small (84 tasks, 6 schemas): wide intervals; tasks of one schema are not independent (we report a schema-cluster bootstrap).
- Public data may be in Apertus' training data (contamination not excluded). The formal terms of the portal could not be read (legal pages unavailable); the datasets are marked CC0 in its metadata.
- With `mlx_lm.server` the model's tool calls arrive as text (`<|tools_prefix|>…`) and are extracted by our own fallback parser; with vLLM they arrive structured.
- Execution speed on the development Mac is low (order of 7 tokens/s measured in a pilot), which bounds how many runs we can afford.
- The local weights are a third-party MLX conversion of the official model; differences from the official gateway are unknown until measured.
- The reasoning setting (`--thinking`) influences results; in a pilot on 8 synthetic tasks the reasoning block never appeared with tools enabled, for either setting.
- Modified weights: WSP technique, strength and format are undecided (TBD). **WSP is a hypothesis.**
